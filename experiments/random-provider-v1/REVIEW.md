# Secure entropy provider proposal

Status: static proposal only. No candidate code has been compiled, executed, linked into a runtime, or timed. `proposal.patch` is reviewable against published commit `37355b7b`; `baseline/` and `proposed/` preserve exact source copies. `manifest.json` records source and immutable runtime hashes. The checked-out runtime source remains unchanged.

The current `cinch_random_bytes` opens `/dev/urandom`, calls `read_exact`, and closes the descriptor for every request, including an empty request. A nonempty successful Linux request therefore normally uses open/read/close. This is a plausible contributor to secure UUID generation cost; the existing measurements do not establish how much of the total cost it explains.

The proposal adds a private entropy module and a Linux-only `sys::getrandom` operation. It reuses the existing inline assembly syscall backend with pinned numbers 318 on x86_64, 278 on aarch64, and 355 on x86. It adds no foreign symbol, external crate, cached descriptor, thread-local state, syscall-number dispatch, or public export. There is no useful SIMD/SWAR operation in this provider: the kernel fills the caller's memory directly. The appropriate fast path is one kernel transition with no per-request descriptor operations.

The closed public ABI remains `#[unsafe(no_mangle)] pub extern "C" fn cinch_random_bytes(n: i64) -> i64`. Negative/unrepresentable lengths still return `-INVALID_ARGUMENT`; allocation behavior remains the same zero-initialized `Vec`. A complete successful fill still moves that vector through `Bytes::from` into `abi::box_bytes`, retaining `KIND_BYTES`, `RC_FRESH`, and the existing `{ len, data }` payload. Errors still pass through the same `io_code` mapping, and an incomplete buffer is dropped without being boxed or exposed. No ownership or layout change is proposed.

The Linux loop advances only by a successful reported count, retries `Interrupted`, rejects zero progress and impossible oversized counts, and falls back only on `ENOSYS` (38). The device fallback receives the unfinished suffix, preserves the completed prefix, and propagates its failure. Permission denial, including a sandbox's `EPERM`, does not trigger an alternate provider. No syscall availability result is cached; on old kernels each draw retries `getrandom` before the existing device path.

An empty public request retains the original device-open check and fresh empty `Bytes` ownership. This deliberately retains its existing failure behavior even though the nonempty fast path can work when `/dev/urandom` is absent. Other hosted platforms keep their existing device path; freestanding targets still exclude the public entropy entry point.

Flags are zero: on supported Linux kernels the call waits until the cryptographic generator is initialized. This is a stronger early-boot readiness policy than the legacy `/dev/urandom` path and must be reviewed as observable behavior. The ENOSYS fallback retains the old device semantics. Successful nonempty calls also stop depending on `/dev/urandom` being mounted or file descriptors being available; that is an intended provider change, not strict equivalence under every filesystem/sandbox configuration.

Static checks to perform before qualification: patch application check, exact baseline hash match, syscall numbers against installed/kernel UAPI tables, and source review of the existing assembly memory/register clobbers. Actual architecture execution, syscall tracing, owned-buffer/leak checks, and performance remain future gates. The existing syscall layer already excludes unsupported Linux architectures; this patch does not expand that claim.

## Deterministic and real-provider gates

The proposed module includes six documented deterministic tests with multiple scenarios. They cover short reads interleaved with interruptions, exact suffix lengths, ENOSYS both before and after progress, exactly one fallback, ten ordinary-error/progress combinations, fallback failure, empty helper loops, zero progress, and oversized counts. Injected bytes are test fixtures for loop control only. They are never used by the real entropy provider or secure generation benchmark.

After a resource grant, first compile a small standalone test wrapper around the copied proposed entropy module. Its `crate::sys::getrandom` stub must panic if called, proving these loop tests cannot accidentally consume or benchmark a replacement provider. Capture the compiler identity, sources, command, exit status, and all test output. This gate does not qualify the real syscall or public ABI.

Next apply the patch only in this lane and build a separately named candidate runtime after explicit resource approval. Run the runtime's platform/sys/bytes/ABI ownership tests, add direct public-boundary checks at lengths -1, 0, 1, 16, 255, 256, 257, 4096, and 1 MiB, free every successful `Bytes`, and run actual `Effect.Random` and UUID public consumers with normal and poisoned allocation/leak checking. Assert exact length, UUID version/variant, and unchanged structured error mapping. Freshness comparisons are smoke checks, not a statistical proof of cryptographic quality. Kernel entropy remains the actual source throughout.

Use a separate process with syscall filtering or a controlled provider shim to verify the real wrapper's ENOSYS fallback and permission-denied failure mapping, without changing sealed runtime inputs. Keep injected-provider tests separately labeled. For the zero-length device-open compatibility check, exercise an isolated mount/path failure condition only if available; otherwise retain this as an explicitly unverified environmental branch. Trace normal real draws in an untimed process: expect one `getrandom` call and no entropy-device open/close for a small nonempty request; expect the existing device open/close for zero length. Inspect the linked candidate symbol/export set and disassembly, then record actual host execution plus available cross-target object checks. A cross-target object alone is not execution evidence.

## Benchmark and resource plan

No timing starts without the parent's exclusive benchmark lease. Use the same frozen compiler, exact same public consumer sources, options, CPU affinity, allocation mode, and benchmark harness on both sides; change only the separately identified runtime archive. Include direct real random bytes at 0, 1, 16, 32, 256, and 4096 bytes, UUID v4, clock-plus-entropy UUID generation, and allocation/control loops. Preserve the existing SDK baseline and all earlier slow results under their original identities. Recompile/relink both sides identically, verify checksums/lengths/version bits before timing, and include real entropy and full allocation/free costs in both reported operations. A native syscall-only diagnostic may help attribution, but must be labeled separately from public pipeline measurements.

Capture pre-start and post-run CPU quota/throttling telemetry, CPU affinity, load, exact compiler/runtime/source/executable hashes, syscall traces outside timing, warmups, all paired raw observations, order, medians, and dispersion. Alternate baseline/candidate ordering across repeated batches. Retain regressions and unstable runs; never normalize away unrelated controls or claim the earlier generation gap is resolved from syscall counts alone.

The static proposal occupies well under 1 MiB. At inspection the shared filesystem had 442 MiB available. Before each future compile, require at least 350 MiB free, reserve 250 MiB, and cap new outputs at 30 MiB per unit. Start with standalone deterministic tests (expected under 10 MiB). A full Cargo runtime build may exceed that budget because the crate emits staticlib, cdylib, and rlib outputs: do not start it until output estimates and a bounded build/staging approach have been approved. No reuse or mutation of a frozen archive is permitted. Remove only newly created reproducible outputs after their provenance/results have been captured; retain failure artifacts and all sealed inputs plain.
